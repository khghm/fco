# راهنمای استقرار (Deployment Guide)

> **وضعیت:** تأییدشده · **نسخه:** v1.1 · **تاریخ:** ۱۴۰۵/۰۹/۰۳
> **مبنا:** Q-11 (یک سرور داخلی + پشتیبان offsite) · `ADR-001` (Modular Monolith) · `ADR-008` (صف در PostgreSQL) · `Architecture-02/SYSTEM_ARCHITECTURE.md §7`
> **قاعده:** این سند **رویه** است؛ تا وقتی دستورها روی محیط واقعی اجرا و ثبت نشوند، استقرار «انجام‌شده» نیست. اعداد ظرفیت در این سند وجود ندارد (اصل ۴).
> **مقادیر سری/رمز در این سند نوشته نمی‌شوند** — فقط نام متغیرها.

---

## ۱. محیط‌ها

| محیط | هدف | داده | دامنه نمونه | دسترسی |
|---|---|---|---|---|
| Development | ساخت روزمره | مصنوعی برچسب‌خورده | `localhost` | محلی |
| Testing | CI | مصنوعی | — | خودکار |
| Staging | بازبینی، Smoke، آزمون امنیتی/بازیابی | بدون PII | `staging.<domain>` | تیم + محدودیت IP |
| Production | بهره‌برداری | واقعی | `<domain>` | عمومی (443 فقط) |

**قواعد:** اسرار و DB هر محیط جدا · Staging هرگز به درگاه Production وصل نمی‌شود · هیچ محیطی از داده Production برای تست استفاده نمی‌کند.

---

## ۲. پیش‌نیازهای زیرساخت (Q-11)

| مورد | الزام | یادداشت |
|---|---|---|
| سرور | Linux LTS، CPU/RAM/دیسک بر اساس **اندازه‌گیری**، نه حدس | مشخصات فنی نهایی باز است |
| دیسک | جدا برای DB و پشتیبان محلی | هشدار فضا در ۷۰٪ (`FM-I-02`) |
| شبکه | 443 عمومی؛ SSH محدود به Bastion/IP مجاز | بدون پورت باز اضافه |
| DNS | رکورد A/AAAA برای دامنه و `www` | TTL کوتاه پیش از تغییر |
| TLS | گواهی معتبر + تجدید خودکار + یادآوری ۳۰ روزه | `FM-I-07` |
| ساعت | NTP فعال (UTC) | صحت Audit و مهلت‌ها |
| پشتیبان offsite | مقصد جدا از سرور + رمزگذاری | `BACKUP_AND_RECOVERY` |
| پایش | دسترسی خروجی برای هشدار (ایمیل/پیام) | بدون PII در پیام هشدار |

## ۳. توپولوژی استقرار

```
Internet ──443──> Reverse Proxy (TLS, HSTS, rate limit, static cache)
                      ├──> app:3000   (web/API — چند نمونه، Readiness)
                      └──> worker     (بدون پورت عمومی)
                                 │
        PostgreSQL 16 (5432، فقط شبکه داخلی) · Redis (کش/قفل، داخلی)
                                 │
                     Backup (محلی + offsite رمزگذاری‌شده)
```
- Proxy تنها نقطه ورودی؛ App و DB روی پورت عمومی گوش نمی‌دهند.
- Worker بدون HTTP عمومی اجرا می‌شود؛ سلامت آن با heartbeat در `job_runs`.
- هیچ Cache در مسیر داده مالی/موجودی به‌عنوان منبع حقیقت استفاده نمی‌شود.

## ۴. متغیرهای محیطی (نام‌ها، بدون مقدار)

| گروه | متغیرها |
|---|---|
| اپ | `NODE_ENV`, `APP_URL`, `APP_TIMEZONE=Asia/Tehran`, `PORT` |
| DB | `DATABASE_URL`, `DATABASE_POOL_MAX` |
| Redis | `REDIS_URL` |
| نشست | `SESSION_SECRET`, `SESSION_TTL_MINUTES` |
| Storage (فاز ۲) | `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` |
| درگاه | `PAYMENT_PROVIDER`, `PAYMENT_BASE_URL`, `PAYMENT_MERCHANT_ID`, `PAYMENT_CALLBACK_SECRET` |
| حمل | `CARRIER_PROVIDER`, `CARRIER_API_KEY`, `CARRIER_WEBHOOK_SECRET` |
| پیامک | `SMS_PROVIDER`, `SMS_API_KEY`, `SMS_SENDER` |
| رصد | `LOG_LEVEL`, `SENTRY_DSN`(اختیاری) |
| صف | `OUTBOX_BATCH_SIZE`, `OUTBOX_MAX_ATTEMPTS` |
| پشتیبان | `BACKUP_TARGET`, `BACKUP_ENCRYPTION_KEY_ID` (کلید در سرویس مخفی) |

**قاعده:** `.env` در مخزن نیست؛ `.env.example` فقط نام و توضیح دارد. تغییر متغیر حساس = چرخش + ثبت در `DECISION_LOG` (بدون مقدار).

## ۵. نصب اولیه (رویه پیشنهادی)

```bash
# ۱) پیش‌نیازها
node -v            # 24.x
npm -v             # 10+/11+

# ۲) دریافت کد و نصب قطعی وابستگی‌ها
git clone <repo> /srv/fco && cd /srv/fco
npm ci

# ۳) پیکربندی (مقادیر در فایل سری، خارج از مخزن)
cp .env.example .env   # سپس مقادیر واقعی در سرویس مخفی/فایل با دسترسی 600

# ۴) ساخت
npm run build

# ۵) Migration (با کاربر Migration، نه کاربر اپ)
npm run db:migrate

# ۶) راه‌اندازی سرویس‌ها (systemd/pm2/containers بر اساس تصمیم استقرار)
npm run start:app
npm run start:worker

# ۷) بررسی سلامت
curl -fsS https://<domain>/health
curl -fsS https://<domain>/health/ready
```
**قاعده:** `npm ci` با lockfile؛ `npm install` روی سرور ممنوع. هر دستور باید exit code صفر بدهد؛ خطا مستند می‌شود، نه نادیده.

## ۶. Reverse Proxy و TLS

| مورد | پیکربندی |
|---|---|
| HTTP → HTTPS | تغییر مسیر دائمی |
| HSTS | `max-age=31536000; includeSubDomains` |
| فشرده‌سازی | brotli/gzip برای متن و استاتیک (نه برای پاسخ حساس) |
| استاتیک | کش طولانی با هش محتوا |
| محدودیت بدنه | سقف آپلود مطابق سیاست فایل |
| نرخ‌محدود | لایه لبه برای `auth`/`otp`/`search` (مکمل محدودیت اپ) |
| هدرها | عبور `X-Request-Id` یا تولید آن؛ حذف هدرهای داخلی |
| Health | مسیر `/health` بدون کش، بررسی از خارج |
| لاگ | ثبت IP واقعی (با اعتماد به proxy فقط از آدرس شناخته‌شده) |

## ۷. رویه انتشار (Release)

```
۱) CI سبز (lint/typecheck/test/migration/build)
۲) ساخت آرتیفکت قابل‌تکرار + ثبت نسخه
۳) Migration افزودنی (Expand) روی Staging → آزمون
۴) انتشار App (چند نمونه، Readiness قبل از ترافیک)
۵) انتشار Worker
۶) Smoke: ورود، محصول، سفارش آزمایشی، پنل، پرداخت Sandbox
۷) Migration پاک‌سازی (Contract) در انتشار بعدی — نه همان انتشار
۸) ثبت Release Notes + نسخه در پنل مدیریت
```

| موضوع | قاعده |
|---|---|
| پنجره انتشار | خارج از ساعات اوج؛ ممنوع در دوره مالی بسته بدون هماهنگی مالی |
| Migration طولانی | خارج از انتشار، با پنجره و پایش قفل |
| Feature Flag | تغییر پرخطر (نرخ مالیات، روش ارسال جدید) پشت flag |
| اطلاع‌رسانی | تغییر مؤثر بر کاربر/مالی اعلام می‌شود |

## ۸. اسموک تست پس از استقرار (حداقل)

1. `/health` و `/health/ready` ⇒ `200`
2. ورود کارمند + MFA + مشاهده مجوزها
3. صفحه یک محصول + قیمت فعال
4. ثبت سفارش آزمایشی با پرداخت Sandbox (`Idempotency-Key`)
5. پنل: صف سفارش، تخصیص، مشاهده Audit
6. Worker: پردازش یک Outbox و ثبت `job_runs`
7. Export کوچک با مجوز

**قاعده:** هر شکست ⇒ Rollback یا توقف انتشار؛ «بعداً بررسی می‌کنیم» مجاز نیست.

---

## ۹. Rollback

| سناریو | اقدام |
|---|---|
| خطای کد | بازگشت به نسخه آرتیفکت قبلی (بدون بازگشت DB اگر Migration افزودنی بود) |
| Migration شکننده | اجرای مسیر بازگشت مستند؛ اگر داده تغییر کرده، بازیابی از پشتیبان طبق `BACKUP_AND_RECOVERY` |
| خطای پیکربندی | بازگشت فایل پیکربندی نسخه‌دار + راه‌اندازی مجدد |
| خطای داده انبوه | توقف نوشتن مربوط (flag) + سند اصلاحی، نه حذف |

**قاعده:** Rollback یک رویه **آزمون‌شده** است، نه امید. پیش از هر انتشار شکننده، مسیر بازگشت مرور می‌شود.

## ۱۰. به‌روزرسانی و نگهداشت دوره‌ای

| دوره | کار |
|---|---|
| روزانه | بررسی سلامت، DLQ، فضای دیسک، خطاهای بحرانی، پشتیبان موفق |
| هفتگی | بازبینی هشدارها، پچ امنیتی، بررسی Jobهای ناموفق |
| ماهانه | آزمون Restore، بازبینی دسترسی‌ها، بررسی گواهی TLS |
| فصلی | آزمون Rollback، بازبینی ظرفیت، بازبینی ریسک |

## ۱۱. چک‌لیست پیش از Production (اولین استقرار)

- [ ] سرور سخت‌سازی‌شده (SSH کلید، فایروال، بدون سرویس اضافه)
- [ ] TLS فعال + HSTS + تجدید خودکار
- [ ] اسرار از مخزن جدا و با دسترسی محدود
- [ ] کاربر DB اپ با حداقل امتیاز؛ کاربر Migration جدا
- [ ] Migration از صفر و روی نسخه قبل آزمون‌شده
- [ ] پشتیبان خودکار + **یک Restore موفق مستند** (`T-DR-01`)
- [ ] پایش و هشدار پایه فعال (خطا، صف، دیسک، Cert)
- [ ] Smoke کامل و ثبت‌شده
- [ ] ADR-007 تأییدشده (نشست/MFA) پیش از فعال‌سازی ورود
- [ ] ADR-009 تأیید مالی پیش از فعال‌سازی COGS
- [ ] هیچ Mock بی‌برچسب در مسیر مشتری

## ۱۲. شکاف‌های باز

1. **سرور Production مشخص نشده** (Q-11 پذیرفته، مشخصات فنی باز) — مسدودکننده استقرار واقعی، نه توسعه.
2. روش اجرای سرویس (systemd/pm2/container) تصمیم نهایی نشده؛ پیشنهاد: container با Compose روی همان سرور.
3. آدرس/ارائه‌دهنده پیامک و درگاه انتخاب نشده (Q-06).
4. پیکربندی WAF/لبه تا انتخاب زیرساخت معلق است.
5. اعداد ظرفیت (تعداد نمونه، pool، batch) پس از اندازه‌گیری تعیین می‌شود.
