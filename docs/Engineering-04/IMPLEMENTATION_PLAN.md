## ۱. اصول اجرا

1. **برش عمودی:** هر تغییر از migration تا UI و آزمون، یک قابلیت قابل‌استفاده تحویل می‌دهد. لایه‌به‌لایه افقی ممنوع.
2. **Migration قبل از کد:** تغییر schema پیش از کدی که به آن وابسته است مرج می‌شود.
3. **بدون دکمه بی‌عملکرد:** UI فقط برای endpoint موجود ساخته می‌شود.
4. **هر تغییر = سند:** رفتار جدید در همان تغییر، سند مربوط را به‌روز می‌کند (اصل ۱۰).
5. **قفل نسخه:** وابستگی جدید نیازمند دلیل و بررسی نگهداشت/امنیت.
6. **مسیر شکست هم تحویل است:** خطا، خالی، عدم دسترسی و حالت Unknown بخشی از تعریف «تمام‌شده» هستند.

## ۳. ساختار مخزن

```
fco/
├─ apps/
│  ├─ shop/                 # فروشگاه (SSR، RTL)
│  ├─ admin/                # پنل مدیریت
│  └─ worker/               # پردازش Outbox/Job (بدون HTTP عمومی)
├─ packages/
│  ├─ domain/               # موجودیت‌ها، قواعد، ماشین وضعیت (بدون I/O)
│  ├─ application/          # use-case + مجوز + تراکنش
│  ├─ infrastructure/       # DB، migration، repository، queue
│  ├─ integrations/         # آداپتور درگاه/حمل/پیامک + Circuit Breaker
│  ├─ contracts/            # schema ورودی/خروجی + openapi.yaml
│  ├─ ui/                   # دیزاین‌سیستم (توکن + مؤلفه)
│  ├─ formatting/           # تاریخ شمسی، مبلغ، عدد، نرمال‌سازی فارسی
│  ├─ config/               # مجوزها، ثابت‌ها، پیکربندی
│  └─ testing/              # fixture، factory، ابزار آزمون
├─ infra/
│  ├─ compose/              # استک توسعه
│  ├─ deploy/               # اسکریپت استقرار/Reverse Proxy
│  ├─ backup/               # اسکریپت پشتیبان/بازیابی
│  └─ monitoring/           # پیکربندی رصد
├─ scripts/                 # ابزار توسعه (seed، smoke، restore-drill)
└─ docs/                    # ۲۰ سند (این مجموعه)
```

**قواعد وابستگی:** `domain` به هیچ‌چیز وابسته نیست · `application` فقط به `domain` · `infrastructure` به `domain/application` · `apps/*` به `application` و `ui` · `integrations` فقط از `application` صدا زده می‌شود.

## ۴. ترتیب اجرایی فاز ۱

### ۴.۱ BR-1 — پایه، هویت، اعتماد

> **مالک جدول ده‌گام و شاهد هر گام:** `Engineering-04/IMPLEMENTATION_START_PLAN.md §3` و ثبت اجرا در `§5` همان سند.
> این سند ترتیب **کلی** را نگه می‌دارد و جدول را تکرار نمی‌کند: مخزن → اسکلت → محیط محلی → Migration پایه → هویت/مجوز → OTP → Audit/تنظیمات → Outbox/Queue/DLQ → رصد و پشتیبان → CI.

**Milestone M1:** کارمند با مجوز محدود وارد می‌شود، عملیات حساسش Audit دارد، Job با DLQ کار می‌کند و بازیابی پشتیبان مستند انجام شده است. تا هر چهار بخش قابل‌نمایش نباشد، BR-1 تمام نیست.

### ۴.۲ BR-2 — کاتالوگ، قیمت، موجودی
1. Migration کاتالوگ/قیمت/موجودی (+ لایه هزینه) → 2. Repository + use-case محصول/تنوع → 3. `inv.apply_movement` اتمیک + رزرو → 4. صفحات عمومی محصول/دسته/جست‌وجو → 5. پنل محصول/قیمت → 6. آزمون هم‌زمانی ۱۰۰/۵.

### ۴.۳ BR-3 — سبد، پرداخت، سفارش
1. Cart/Quote سرور → 2. `place-order` با Idempotency → 3. آداپتور درگاه + Callback امن + حالت Unknown → 4. ماشین وضعیت + `/transitions` → 5. صف تخصیص.

### ۴.۴ BR-4 — انبار تا تحویل
Pick List/اسکن → بسته‌بندی/وزن → مرسوله/لیبل → Manifest + سند ارسال (خروج موجودی + COGS) → رهگیری مشتری.

### ۴.۵ BR-5 — پس از فروش و مالی اولیه
انصراف → RMA/بازرسی → استرداد یکتا → فاکتور داخلی + سند مالی + COGS از لایه هزینه.

## ۶. CI و گیت‌های کیفیت

```
install (lockfile) → lint → typecheck → unit → integration (DB واقعی) → migration up/down
→ build → contract/E2E بحرانی → بازرسی وابستگی/اسرار
```
| گیت | شرط عبور |
|---|---|
| Lint/Type | صفر خطا |
| Unit | همه سبز؛ پوشش قواعد دامنه (نه درصد کلی به‌عنوان هدف) |
| Integration | migration از صفر + آزمون تراکنش/Outbox |
| Security | `T-SEC-*` سبز |
| Build | خروجی قابل‌تکرار با lockfile |
| قرمز عمدی | یک بار آزمون به‌صورت آگاهانه شکسته تا CI قرمز شود (اثبات کارکرد گیت) |

**سیاست شاخه:** شاخه کوتاه‌عمر + بازبینی؛ ادغام فقط با CI سبز؛ بدون force-push روی `main`؛ هر commit پیام معنادار.
