# معماری امنیت (Security Architecture)

> **وضعیت:** تأییدشده (G0) · **نسخه:** v1.1 · **تاریخ:** ۱۴۰۵/۰۹/۰۳
> **مرجع بالادست:** `Architecture-02/SYSTEM_ARCHITECTURE.md §6` · **مجوزها:** `Business-01/USER_ROLES_AND_PERMISSIONS.md`
> **قاعده:** امنیت یک لایه نیست، یک ویژگی در هر لایه است. هر کنترل این سند باید **آزمون** داشته باشد (`Engineering-04/TEST_STRATEGY.md §6`)، وگرنه وجود ندارد.
> **وضعیت:** طرح. هیچ کنترل پیاده‌سازی‌نشده «فعال» شمرده نمی‌شود.
> **مالک تهدید، احراز هویت، رمزنگاری، امنیت عملیات و `T-SEC-*`.**

---

## ۱. مدل تهدید (STRIDE روی سطح واقعی پروژه)

| تهدید | نمونه در FCO | کنترل | FM |
|---|---|---|---|
| **S**poofing | جعل نشست، ورود با Credential لو‌رفته | Argon2id، MFA برای نقش حساس، قفل تدریجی، هشدار ورود | FM-S-07 |
| **T**ampering | دستکاری قیمت/مبلغ در کلاینت، دستکاری پیکربندی مالیات | محاسبه مجدد سرور، قاعده نسخه‌دار، Audit | FM-S-03، FM-F-04 |
| **R**epudiation | انکار ثبت سند/تأیید پرداخت | Audit تغییرناپذیر با actor/IP/request_id | FM-Z-02 |
| **I**nformation disclosure | IDOR سفارش، نشت PII در لاگ/Export | مالکیت منبع، Redaction، مجوز Export | FM-S-01، FM-S-05، FM-S-08 |
| **D**enial of service | ارسال انبوه OTP/پیامک، جست‌وجوی سنگین | نرخ‌محدود، صف، Circuit Breaker | FM-S-04 |
| **E**levation of privilege | تخصیص نقش به خود، دور زدن SoD | تفکیک وظایف در Application + DB | FM-H-06 |

### ۱.۱ دارایی‌های حساس (به ترتیب اهمیت)
1. اسناد مالی و دفتر کل (یک‌بار خراب = ماه‌ها بی‌اعتمادی)
2. دفتر موجودی و رزروها (oversell = تعهد به مشتری)
3. PII مشتریان (موبایل/آدرس/تاریخچه خرید)
4. اسرار (کلید درگاه، کلید پشتیبان، رمز DB)
5. داده کاتالوگ/قیمت (مزیت رقابتی)

### ۱.۲ مرزهای اعتماد
```
[مرورگر] ──TLS──> [Reverse Proxy] ──> [App] ──> [PostgreSQL]
                                            └──> [Worker] ──> [سرویس بیرونی]
[TMS/Bastion] ──> [میزبان] (دسترسی DB فقط از شبکه/تانل، هرگز از اینترنت)
```
- مرورگر **هرگز** به DB، Redis یا Storage دسترسی مستقیم ندارد.
- Worker با همان اعتبار App کار می‌کند ولی با نقش عملیاتی محدود (`app_worker`).
- سرویس‌های بیرونی فقط از طریق `Integration Hub` با اعتبار اختصاصی و Circuit Breaker.

## ۲. احراز هویت

| مورد | تصمیم | جزئیات |
|---|---|---|
| رمز کارکنان | Argon2id (fallback bcrypt با cost>=12) | پارامترها مستند و قابل افزایش با زمان |
| سیاست رمز | حداقل طول، بررسی رمزهای رایج، بدون انقضای اجباری دوره‌ای (توصیه NIST) | تغییر اجباری حداقل یک‌بار پس از ایجاد حساب |
| MFA | TOTP | الزامی برای R-CEO/R-FIN/R-ACC/R-SYS/R-SALES/R-WH/R-SUP/R-MKT |
| ثبت‌نام | فقط با دعوت مدیر (بدون ثبت‌نام خودکار کارمند) | `iam.user.create` |
| OTP مشتری | ۶ رقم، TTL کوتاه، حداکثر تلاش، نرخ‌محدود | پاسخ یکسان برای موبایل موجود/غیرموجود |
| بازیابی رمز | توکن یک‌بارمصرف، پاسخ ثابت | بدون افشای وجود حساب (`FR-1-08`) |
| ورود ناموفق | قفل تدریجی + ثبت + هشدار | `failed_attempts`/`locked_until` |
| نشست | کوکی `HttpOnly; Secure; SameSite=Lax`، چرخش پس از ورود، ابطال مرکزی | `ADR-007` (پیشنهادی؛ تأیید پیش از گام ۵) |
| خروج | ابطال نشست جاری + امکان «خروج از همه دستگاه‌ها» | `iam.session.revoke` |

**ممنوع:** نگهداری توکن در `localStorage`، JWT بی‌وضعیت بدون ابطال، رمز عبور در لاگ/URL/پارامتر.

## ۳. مجوزدهی

سه‌لایه (تفصیل در `USER_ROLES_AND_PERMISSIONS.md`):
1. **مجوز عملیات:** `domain.action` از `sys_permission` (نه هارد‌کد نام نقش).
2. **مالکیت منبع:** هر رکورد با `owner_id`/`warehouse_id`/`team_id` فیلتر می‌شود؛ شناسه دستکاری‌شده ⇒ `404` (نه `403`، برای عدم افشای وجود).
3. **تفکیک وظایف:** قید DB (`created_by <> approved_by`) علاوه بر بررسی لایه برنامه.

**قاعده پیاده‌سازی:** بررسی مجوز در **use-case** انجام می‌شود، نه در route؛ بنابراین CLI، Job و Import هم همان کنترل را دارند. یک میان‌افزار مجوز برای همه مسیرها ممنوع است (خطر فراموشی).

## ۴. حفاظت ورودی و خروجی

| ریسک | کنترل |
|---|---|
| SQL Injection | پارامتری‌سازی اجباری؛ هیچ رشته SQL با ورودی ساخته نمی‌شود؛ ORM با query builder امن |
| XSS | رمزگذاری خروجی در قالب؛ CSP سختگیرانه؛ `dangerouslySetInnerHTML` فقط با sanitizer و بازبینی |
| CSRF | SameSite + بررسی `Origin`/`Sec-Fetch-Site` برای متدهای تغییردهنده |
| SSRF | آدرس‌های بیرونی از allowlist دامنه؛ بدون پذیرش URL دلخواه کاربر برای fetch |
| Path Traversal | کلید فایل تولیدشده سرور (تصادفی)، نه نام کاربر؛ دسترسی با شناسه |
| Mass Assignment | schema صریح ورودی (allowlist فیلد)، نه bind مستقیم |
| ReDoS | regex محدود، محدودیت طول ورودی |
| Header Injection | sanitize هدرها، بدون echo ورودی در هدر |
| Upload مخرب | بررسی نوع واقعی (magic bytes)، نام تصادفی، ذخیره خارج از webroot، `Content-Disposition: attachment`، ممنوعیت اجرا، محدودیت حجم |
| Open Redirect | مسیر بازگشت فقط داخلی و از allowlist |

### ۴.۱ هدرهای امنیتی (الزامی)
```
Strict-Transport-Security: max-age=31536000; includeSubDomains
Content-Security-Policy: default-src 'self'; img-src 'self' data:; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; base-uri 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), camera=(), microphone=()
X-Frame-Options: DENY
```
> `unsafe-inline` در استایل تنها با دلیل مستند؛ `unsafe-eval` ممنوع.

## ۵. مدیریت نشست و توکن

| موضوع | قاعده |
|---|---|
| ذخیره | فقط `token_hash` (SHA-256 با نمک سراسری) در `iam.sessions` |
| انقضا | مطلق + بی‌فعالیتی؛ تمدید فقط با استفاده واقعی |
| چرخش | پس از ورود، پس از تغییر رمز/نقش، پس از MFA |
| ابطال | خروج، تغییر رمز، غیرفعال‌سازی کاربر، حادثه امنیتی |
| هم‌زمانی | حداکثر تعداد نشست فعال قابل پیکربندی |
| کوکی | `Secure` در همه محیط‌ها به‌جز localhost؛ `SameSite=Lax`؛ دامنه محدود |
| API ماشین‌به‌ماشین | کلید/توکن اختصاصی با scope، چرخش دوره‌ای، IP allowlist در صورت امکان |

## ۶. رمزنگاری

| مورد | الگوریتم/روش |
|---|---|
| انتقال | TLS 1.2+ (ترجیح 1.3)، HSTS، بدون Mixed Content |
| رمز عبور | Argon2id (یک‌طرفه) |
| داده در حال استراحت | رمزنگاری دیسک/Volume در سطح زیرساخت |
| پشتیبان | رمزگذاری با کلید مستقل از سرور (offsite)، کلید جدا از داده |
| اسرار برنامه | متغیر محیطی/فایل سری با دسترسی محدود؛ هرگز در مخزن |
| امضای Webhook | HMAC-SHA256 روی بدنه خام + timestamp |
| شناسه‌های عمومی | UUID تصادفی، بدون شماره ترتیبی قابل حدس |
| PII در لاگ | ماسک/حذف (`FM-S-05`) |

**قاعده کلید:** چرخش کلید مستند و آزمون‌شده؛ هیچ کلیدی در کد یا سند نوشته نمی‌شود. `ADR-010` مدت نگهداشت کلید/داده را تعیین می‌کند.

## ۷. امنیت عملیات (Operational Security)

| موضوع | قاعده |
|---|---|
| دسترسی سرور | SSH کلید‌محور، بدون رمز، Bastion، MFA، حداقل کاربر |
| دسترسی DB | فقط از شبکه داخلی/تانل؛ کاربر اپ با حداقل امتیاز (`DML` روی schemaهای لازم، بدون `SUPERUSER`/`DDL`) |
| کاربر Migration | جدا از کاربر اپ، فقط در پنجره استقرار |
| Firewall | فقط 443 عمومی؛ پورت‌های داخلی بسته |
| پچ | به‌روزرسانی امنیتی دوره‌ای + ثبت نسخه |
| اسکن وابستگی | در CI؛ نسخه قفل‌شده؛ آینه داخلی در صورت قطع دسترسی |
| اسکن اسرار | pre-commit + CI؛ نشت ⇒ چرخش فوری (`FM-S-09`) |
| لاگ دسترسی | ثبت ورود مدیریتی، تغییر پیکربندی، Export |
| محیط Staging | بدون PII واقعی؛ داده مصنوعی برچسب‌خورده |

## ۸. لاگ، پایش و کشف

| سیگنال | محتوا | هشدار |
|---|---|---|
| ورود ناموفق | actor, IP, agent, نتیجه | نرخ غیرعادی |
| تغییر مجوز | قبل/بعد، actor، دلیل | هر مورد به R-CEO |
| Export/PII | actor، ستون‌ها، دلیل، حجم | حجم غیرعادی |
| خطای 4xx/5xx | code، request_id، مسیر | جهش نرخ |
| Callback نامعتبر | provider، دلیل رد، IP | هر مورد |
| Circuit Breaker باز | سرویس، مدت | بیش از آستانه |
| تغییر تنظیمات مالی/مالیاتی | key، نسخه، actor | هر مورد |

**قاعده لاگ:** ساختاریافته (JSON)، `request_id` در همه رکوردها، بدون PII/توکن/بدنه کامل درخواست حساس، نگهداشت طبق `ADR-010`، دسترسی خواندن محدود به R-SYS.

## ۹. امنیت داده و حریم خصوصی

| مورد | قاعده |
|---|---|
| حداقل‌سازی | فقط داده‌ای که برای عملیات لازم است جمع می‌شود |
| ماسک پیش‌فرض | موبایل/ایمیل/آدرس در لیست‌ها ماسک؛ افشا با مجوز و دلیل |
| رضایت | ثبت Consent با تاریخ/کانال/متن نسخه‌دار (`FR-11-06`) |
| حذف/بی‌هویت‌سازی | طبق `ADR-010`؛ سند مالی حفظ، PII بی‌هویت؛ Audit اجباری |
| Export | مجوز جدا، لینک موقت، ثبت دلیل، محدودیت ستون |
| محیط تست | بدون داده واقعی؛ اگر لازم شد، بی‌هویت‌شده و برچسب‌خورده |
| اشتراک‌گذاری با سرویس بیرونی | فقط حداقل فیلد لازم (مثلاً موبایل برای پیامک) |

## ۱۰. امنیت یکپارچگی بیرونی

| کنترل | جزئیات |
|---|---|
| Timeout | اجباری برای هر فراخوانی؛ بدون Timeout ممنوع |
| Retry | فقط برای عملیات idempotent، با backoff و سقف |
| Circuit Breaker | باز شدن پس از نرخ خطای آستانه؛ پیام کاربر قابل‌فهم و بدون جزئیات فنی |
| اعتبارنامه | اختصاصی هر سرویس، در مخزن اسرار، چرخش دوره‌ای |
| امضای ورودی | Webhook با HMAC + timestamp + کلید یکتا |
| بازپخش | `provider_ref`/`event_id` یکتا ⇒ رد تکراری |
| ذخیره خام | بدنه خام برای بازبینی، با نگهداشت محدود |
| Sandbox/Production | اعتبارنامه و آدرس جدا؛ هیچ Fallback خودکار به Production |

## ۱۱. آزمون امنیتی (الزامی پیش از هر انتشار)

| # | آزمون | انتظار |
|---|---|---|
| `T-SEC-01` | هر endpoint حساس بدون مجوز | `403 FCO-1003` |
| `T-SEC-02` | منبع متعلق به کاربر دیگر (IDOR) | `404` بدون داده |
| `T-SEC-03` | تأیید توسط خود (SoD) | رد در Application + DB |
| `T-SEC-04` | لاگ با ورودی حاوی PII | ماسک‌شده |
| `T-SEC-05` | نشست ابطال‌شده/منقضی | `401` |
| `T-SEC-06` | ورود نقش حساس بدون MFA | مسدود |
| `T-SEC-07` | تغییر تنظیمات مالی بدون مجوز | `403` |
| `T-SEC-08` | Callback بدون امضا/تکراری | `401` + بدون اثر |
| `T-SEC-09` | آپلود فایل با پسوند فریب‌دهنده | `415` |
| `T-SEC-10` | درخواست با Origin خارجی (CSRF) | `403` |
| `T-SEC-11` | Export PII بدون مجوز | `403` + ثبت تلاش |
| `T-SEC-12` | Brute Force OTP | محدودیت + قفل |

**قاعده:** آزمون امنیتی که هرگز قرمز نشده، اعتبار ندارد؛ در محیط Staging یک بار کنترل را آگاهانه بشکنید تا آزمون قرمز شود.

## ۱۲. پاسخ به حادثه (خلاصه اجرایی)

```
کشف → ارزیابی شدت → مهار (flag/قطع دسترسی) → حفظ شواهد (لاگ/بدنه خام)
     → رفع ریشه‌ای → بازسازی داده (سند اصلاحی) → اطلاع‌رسانی → درس‌آموخته
```
| شدت | مثال | زمان واکنش | اطلاع |
|---|---|---|---|
| S1 | نشت PII، سند نادرست انبوه، دسترسی غیرمجاز | فوری | مالک + TECH |
| S2 | قطعی درگاه، DLQ انبوه | ۳۰ دقیقه | TECH |
| S3/S4 | خطای محدود | همان روز | سرپرست |

جزئیات رویه در `Engineering-04/BACKUP_AND_RECOVERY.md §8` و `RISK_REGISTER`.

## ۱۳. شکاف‌ها و تصمیم‌های باز

1. **ADR-007 (کوکی + MFA) هنوز «پیشنهادی» است** — مسدودکننده گام ۵ از BR-1؛ باید پیش از پیاده‌سازی تأیید شود.
2. سیاست دقیق نگهداشت لاگ دسترسی و PII منتظر تأیید LEG-EXT (ADR-010).
3. الزام قانونی گزارش رخداد داده (در صورت وجود) بررسی نشده — نیازمند مشاور حقوقی.
4. نبود WAF/rate-limit لبه تا مشخص‌شدن زیرساخت Q-11؛ فعلاً محدودیت در لایه App.
5. آزمون نفوذ (Pen-test) برنامه‌ریزی نشده؛ پیشنهاد: پیش از G1 روی Staging.
